An agent can change a composed card Windows already shows by sending only what changed (core v0.19.0, ourostack/ouro-ui-core#94).

- **Tree updates.** `OuroComposed.ApplyTreeUpdate` ports core's `applyTreeUpdate`: an update `{ nodes?, data? }` replaces nodes by id and sets the data model by JSON pointer.
  - It applies all or nothing, and never changes its inputs.
  - An id the card lacks or a template's instances share is refused, and so is an unsafe path.
  - The updated tree passes every check a whole tree does, so an update can't relabel a button or loosen its consent.
  - `OuroComposedResult.Update` reads an update from a tool result's `structuredContent.ouro.update`.
- **`OuroComposedSurface` takes an update** through `Show(catalog, result)` or `Update(update)`.
  - What the person entered stays, except where the agent changed the value or the list item it sits in (`OuroComposed.KeepAnswers`, as web's `ComposedSurface` does).
  - A tree or an update that fails the checks shows one short alert, "This card can't be shown"; an invalid tree used to show nothing.
  - A refused update keeps the last card, hidden, with the person's answers, so a corrected update applies to it.
  - Keyboard focus returns to the field that had it.
- **Ouro Shop** shows an agent updating its card, and refusing an update for a node the card lacks.
- Core v0.19.0 is vendored by tag and SHA-256, with its tree update cases from the tag.

## How it was checked

- **Unit tests** (CI's `actions` job): all five of core's update cases give exactly their expected tree and data or problems. The tests also cover core's update tests, Ouro Shop's two updates and the answer-keeping rule.
- **On `windows-latest`** (the `windows` job): CI types into Ouro Shop's card, then applies the agent's update, refuses the bad one, and applies the good one again. It reads the card through UI Automation after each step.

The limits in v0.2.0's notes still hold.
